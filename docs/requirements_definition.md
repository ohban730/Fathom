## 1. プロジェクト概要

### 1.1 背景と課題

バイブコーディング（AIによるコード生成）の普及により、開発者が **自身の書いていないコードを正確に理解しないまま利用する「理解負債」** が蓄積している。既存のAIツール（Claude、Codex等）はコードの「解説」を出力できるが、開発者が **本当に理解したかどうかを測定・検証する仕組み** は存在しない。

### 1.2 プロダクトビジョン

**理解負債の発生を防止・測定・管理するシステム**（管理番号9）

単なるコード解説ではなく、**能動学習（アクティブラーニング）とテスト** によって、開発者のコード理解度を定量的に評価し、理解の定着を支援する。

### 1.3 Phase 1 の目的と完了条件（管理番号10-1）

- **目的**: 1つのPythonファイルを対象に、質問→回答→採点の最小ループを動かし、「コード理解の深まり」を自分自身で体感できるか検証する。
- **完了条件（4基準）**:
  1. LLMが的外れでない質問を生成できること
  2. 採点とフィードバックの理由が納得できること
  3. 2回目の回答でスコアが上がる（学び直しループが機能する）こと
  4. 終了後に「このコードを説明できる」自信がつくこと

## 3. 機能要件

### FR-01: 対象ファイル選択とAST分割
- ユーザーが理解したい対象ファイル（またはフォルダ）を選択する。
- Python標準の `ast` モジュールを利用し、関数（`FunctionDef`）およびクラス（`ClassDef`）単位でChunkに分割する。
- ファイル変更検知のため、ファイルのハッシュ値（`file_hash`）を取得・保存する（管理番号3-2-1-3）。

### FR-02: 条件設定（基準点・モード）
- LLMが再テストするかの判断基準となる合格点数（10〜100点）を設定する。
- 学習モード（ざっくり/しっかり/弱点克服）を選択可能とし、バックエンドでプロンプトの初期パラメータを切り替える（管理番号3-2-1-4）。

### FR-03: 質問生成と図表示
- LLMがAST Chunkを読み取り、理解軸（構造軸：処理内容、関係軸：呼び出し関係）に応じた質問を生成する。
- 同一Chunk内では段階的エスカレーション（基礎→標準→応用）を行い、難易度（`difficulty`）を付与する。
- 必要に応じてMermaid図（フローチャートやシーケンス図）を自動生成して表示する。

### FR-04: ユーザー回答入力
- ユーザーは質問に対して文章形式で回答を入力する（コード入力は行わない）。

### FR-05: 理由付き採点・フィードバック
- LLMはユーザー回答を採点し、100点満点のスコアを算出する。
- **透明性の確保**: 「なぜその点数か」が納得できるよう、項目別スコアと具体的な理由（`score_details`）をJSONで出力・表示する（管理番号9-1-4）。
- **考え方の癖分析準備**: ミスの分類タグ（`miss_categories`）を出力・保存する（管理番号3-2-1-3）。
- **体験設計原則**: 抽象的な褒めを避け、出来ている点を客観的に伝えた上で「次の一手」のヒントを提示する（管理番号4-2-1-1）。

### FR-06: 合否判定と学び直しループ
- スコア ≥ 基準点 → 合格表示（次のChunkへ）。
- スコア < 基準点 → 不合格表示（フィードバックとヒントを提示し、再回答を促す）。

### FR-07: 中断・再開
- 中断ボタン等でいつでもセッションを終了でき、SQLiteに保存された状態から後で再開できる。

## 4. 非機能要件

### NFR-01: 技術スタック・アーキテクチャ
- **UI**: Streamlit（Phase 1）。プロトタイプ検証後にVS Code拡張へ移行。
- **ロジック**: Python (`ast` モジュール等)。
- **LLMエンジン**: ローカルLLM（Ollama優先）。`LLMClient` 抽象層を挟んで将来のAPI切り替えに対応。
- **データ層**: SQLite（単一ファイル、パス参照方式）。

### NFR-02: ローカル完結・セキュリティ/ガバナンス
- すべての処理はユーザーのローカル環境（localhost）で完結する。
- Phase 1におけるガバナンス・セキュリティは必要最小限（localhostバインド、プレースホルダ利用、.gitignore設定）とし、本格対応はPhase 2まで凍結する。

### 6.2 機能要件

#### FR-08: 拡張機能UIの提供
- `WebviewViewProvider`として、VS CodeのPanel領域（`viewsContainers.panel`。TERMINAL等と同じ場所）にUIを表示する。サイドバーやエディタ列（`ViewColumn`）は使用しない。
- `retainContextWhenHidden: true`相当の挙動（Panel切り替え後も状態を保持）とする。

#### FR-09: バックエンドの自動起動
- 拡張機能の`activate()`時に、`vscode-extension/main.py`（FastAPI）をサブプロセスとして自動起動する。
- ポートは固定せず、都度空きポートを動的に確保する。
- 使用するPython実行体は`fathom.pythonPath`設定でユーザーが明示指定する（未設定時はエラーメッセージで案内。自動検出は行わない）。

#### FR-10: アクティブファイルへの自動追従
- `onDidChangeActiveTextEditor`で`.py`ファイルへの切り替えを検知し、Webviewへ自動反映する。
- 対象はワークスペースフォルダの内外を問わない（絶対パスで動作するため、今開いているフォルダと無関係な場所のファイルも制限なく対象にできる）。

#### FR-11: 星座マップによるChunk可視化
- AST解析されたChunk（関数/クラス/エントリーポイント）を星として配置し、`calls`（呼び出し関係）を線で結ぶ。
- 合格/要復習/現在地/未探索をアイコン・色で区別する。

#### FR-12: 最近テストしたファイルの一覧・再選択
- `GET /api/projects/recent`で、`sessions.started_at`基準の直近テスト順にファイル一覧を取得する。
- パネル内のボタン、またはコマンドパレット（`Fathom: 最近テストしたファイルを開く`）から、クイックピックで選択し直接開ける。フォルダをまたいで一覧表示される。

#### FR-13: ワークスペースへのフォルダ追加
- パネル内のボタンから、VS Code標準コマンド`workbench.action.addRootFolder`を呼び出し、ワークスペースにフォルダを追加できる。

#### FR-14: ステータスバーでの進捗表示
- 現在の対象ファイル名と進捗（`current`/`total` Chunk数）をステータスバーに表示する。
- クリックでFathomパネルを開く。

### 6.3 非機能要件

#### NFR-03: 配布パッケージへのバックエンド同梱
- `fathom/`パッケージと`main.py`は`vscode-extension/`配下に配置する。`vsce package`は`vscode-extension/`配下のみをパッケージ化するため、この配置でないと配布物にPythonバックエンドが含まれない。

#### NFR-04: ローカル通信のみ
- 拡張ホスト⇔Webview間はVS Codeの`postMessage`のみ。Webview⇔バックエンド間は`http://127.0.0.1:<動的ポート>`のローカルHTTPのみで、外部通信は行わない（Phase 1のNFR-02「ローカル完結」方針をPhase 3でも継続）。
- **強制方法**（2026-08-13追加）: この要件は長らくドキュメント上の約束にとどまっており、実際にはWebviewがTailwind CSS・Mermaid.js・Google Fontsを外部CDNから読み込んでいて違反していた。現在は次の2点で実行時に強制している。
  - 3つの依存をすべて`vscode-extension/media/vendor/`に同梱し、CDN参照を廃止した（Tailwindは`tailwind.config.js`でローカルビルド。`npm run build:css`）。
  - `index.html`に`default-src 'none'`起点のCSPを設定し、`${cspSource}`（拡張機能の同梱リソース）と`connect-src http://127.0.0.1:*`（ローカルバックエンド）以外を全遮断した。以後、外部CDNへの参照を足しても実行時にブロックされる。
- **例外**: 苦手タグの「🌐 検索」リンク（`<a target="_blank">`でGoogle検索を開く）のみ外部に出る。これはユーザーの明示的なクリックでVS Code外のブラウザを開く動作であり、拡張機能自身がバックグラウンドで通信するものではないため、本要件の対象外とする。

#### NFR-05: Chunk境界の安定性
- `if __name__ == "__main__":`等のエントリーポイントブロックは第一級のChunkとして扱い、再解析時にもChunk境界（星の位置）が安定するようにする（`CLAUDE.md`の「Python Chunk Parsing」規約に対応）。
