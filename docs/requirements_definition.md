## 1. プロジェクト概要

### 1.1 背景と課題

バイブコーディング（AIによるコード生成）の普及により、開発者が **自身の書いていないコードを正確に理解しないまま利用する「理解負債」** が蓄積している。既存のAIツール（Claude、Codex等）はコードの「解説」を出力できるが、開発者が **本当に理解したかどうかを測定・検証する仕組み** は存在しない。

### 1.2 プロダクトビジョン

**理解負債の発生を防止・測定・管理するシステム**（管理番号9）

単なるコード解説ではなく、**能動学習（アクティブラーニング）とテスト** によって、開発者のコード理解度を定量的に評価し、理解の定着を支援する。

### 1.3 差別化方針（管理番号9-1）

| 比較軸 | 既存ツール（Copilot, Cursor等） | 本システム |
|:---|:---|:---|
| 主機能 | 生成・補完（スピード） | 能動学習・テスト（教育） |
| アプローチ | 受動的（解説を読む） | 能動的（質問に答える） |
| 評価 | なし | 採点・スコアリング・トラッキング |
| 独自性 | — | 評価アルゴリズムと理解度トラッキング |

## 2. 用語定義

| 用語 | 定義 | 管理番号 |
|:---|:---|:---:|
| コード理解 | 既にある動くプログラムの流れを何も見ずに他人に説明でき、かつ何も見ずにプログラムを再現できること | 1 |
| 助けてくれる | 色んな視点・角度から質問をユーザーに投げて、回答できるかを判定すること | 2 |
| AIエージェント | LLMがサービスに組み込まれたもの | 3 |
| プログラムの流れ | プログラムで定義する処理の内容と順番のこと | 1-1 |
| 説明 | 必要に応じて図を使いながら口頭または文章で行う行為 | 1-2 |
| 理解負債 | バイブコーディングで作ったコードに対する理解不足の蓄積 | 6 |
| 論理的内容 | 処理の塊として適切な範囲でまとめた説明 | 1-1-1 |
| 物理的内容 | 最低限、関数単位で何を実行するか（引数含む） | 1-1-1, 1-4 |

## 4. 機能要件

### FR-01: 対象ファイル選択

| 項目 | 内容 |
|:---|:---|
| 概要 | ユーザーが理解したい対象のファイルまたはフォルダを選択する |
| 入力 | ファイルパス or フォルダパス |
| 処理 | ローカルファイルを直接読み込み、関数/クラス単位でChunk分割 |
| 出力 | 学習対象Chunkリスト |
| 管理番号 | 5, 7（フロー①） |

### FR-02: 合格基準点設定

| 項目 | 内容 |
|:---|:---|
| 概要 | LLMが再テストするかの判断基準となる点数をユーザーが設定する |
| 入力 | 数値（点数） |
| 出力 | セッションへの基準点登録 |
| 管理番号 | 7（フロー②） |

### FR-03: 質問生成

| 項目 | 内容 |
|:---|:---|
| 概要 | LLMが対象コードを読み取り、理解度を測る質問を生成する |
| 質問観点 | **論理的内容**（処理の塊の流れ）と **物理的内容**（関数単位・引数含む）の2観点 |
| 図表示 | プログラムをMermaid図に変換して表示 |
| プロンプト | Few-Shot例を2〜3パターン記述（良い質問例） |
| 管理番号 | 1-1-1, 1-2-1, 3-1, 7（フロー③） |

### FR-04: ユーザー回答入力

| 項目 | 内容 |
|:---|:---|
| 概要 | ユーザーが質問に対して文章で回答する |
| 入力形式 | テキスト入力（文章） |
| 備考 | コードを書かせるのではなく、説明として物理的内容を引数含めて記述させる |
| 管理番号 | 1-2, 1-4, 7（フロー④） |

### FR-05: 回答採点・フィードバック

| 項目 | 内容 |
|:---|:---|
| 概要 | LLMがユーザーの回答内容を採点し、フィードバックを返す |
| 入力 | 質問 + ユーザー回答 + 元のコード |
| 出力 | スコア（数値） + フィードバックテキスト |
| プロンプト | Few-Shot例を2〜3パターン記述（採点例） |
| 管理番号 | 3-1, 7（フロー⑤） |

### FR-06: 合否判定・再テストループ

| 項目 | 内容 |
|:---|:---|
| 概要 | 設定した基準点を下回った場合、ユーザーに再度回答させる |
| 判定ロジック | スコア ≥ 基準点 → 合格（次のChunkへ）、スコア < 基準点 → 不合格（再回答） |
| ループ | 全Chunkをカバーするか、ユーザーが中断するまで継続 |
| 管理番号 | 7（フロー⑥⑦） |

### FR-07: 中断・再開

| 項目 | 内容 |
|:---|:---|
| 概要 | ユーザーが任意のタイミングで理解タスクを中断し、後から再開できる |
| 中断方法 | 中断ボタン、またはアプリを閉じる |
| 再開 | DBに保存された進捗状態から再開 |
| 管理番号 | 7-1 |

### FR-08: 学習履歴管理

| 項目 | 内容 |
|:---|:---|
| 概要 | 質問・回答・スコア・フィードバックのセット（履歴）をローカルDBに保存する |
| 保存対象 | 理解負債対象ファイル（パス参照）、LLM出力データ、ユーザー入力データ、採点・判定データ |
| 方針 | ソースコード本体はDBに保存せず「パス参照」に留める |
| 管理番号 | 8, 8-1 |

## 5. 非機能要件

### NFR-01: デプロイ形態

| 項目 | 内容 |
|:---|:---|
| Phase 1 | Streamlit（Python）によるプロトタイプ |
| Phase 3 | VS Code拡張機能として構築 |
| 理由 | デスクトップアプリは開発コストが膨れ上がるため段階的に移行 |
| 管理番号 | 4, 4-1, 4-2 |

### NFR-02: LLMエンジン

| 項目 | 内容 |
|:---|:---|
| 方式 | ローカルLLM使用（Ollama等） |
| 代替 | Claude / OpenAI APIも選択肢 |
| 台数 | 1つのLLMを使用し、プロンプトで質問/採点タスクを分離 |
| 管理番号 | 3-2, 5-1 |

### NFR-03: 利用モード

| 項目 | 内容 |
|:---|:---|
| 方式 | 開発作業と学習タイミングを **完全に分離** する（アプローチB） |
| 理由 | バイブコーディングや普段の開発中に利用が億劫になるため |
| 管理番号 | 9-2, 5-3 |

### NFR-04: UIの必須条件（管理番号5-5）

以下の3点は **絶対に譲れない** UI要件：

1. LLMから投げられた **質問を表示** すること
2. 必要に応じて **図が使えて、回答を文字で入力** できること
3. **入力内容が表示** されること

### NFR-05: コスト

| 項目 | 内容 |
|:---|:---|
| UI構築 | UIを一から作るコストは受け入れられない（管理番号5-2） → Streamlit採用 |
| API課金 | ローカルLLM優先で従量課金コストを回避（管理番号4） |

### NFR-06: 配布・保守

| 項目 | 内容 |
|:---|:---|
| Phase 1 | ローカル実行（保守不要） |
| Phase 3候補 | VS Code Marketplace経由の配布、またはWebアプリ化（管理番号5-4） |
| 技術的制約 | HTML/CSS/JSの経験が少ないため、Python中心の技術選定（管理番号5-4） |

## 6. データ要件

### 6.1 管理対象データ（管理番号8）

| データ種類 | 説明 |
|:---|:---|
| 理解負債対象ファイル | ファイルパス参照（本体はDB保存しない） |
| LLM出力データ | 質問テキスト、Mermaid図、フィードバック |
| ユーザー入力データ | 回答テキスト |
| 採点・判定データ | スコア（数値）、合否フラグ |

### 6.2 データ保存方針（管理番号8-1）

1. 基本は **ローカルDB（SQLite）** で一括管理
2. ソースコード本体はDBに保存せず **「パス参照」** に留める
3. **質問・回答・スコアのセット（履歴）** のみをDBに記録

## 7. 操作フロー（管理番号7）

| ステップ | 操作 | 詳細 |
|:---:|:---|:---|
| ① | 対象選択 | 理解したい対象であるフォルダまたはファイルを選択する |
| ② | 基準点設定 | LLMが再テストするかの判断基準となる点数を設定する |
| ③ | 質問表示 | 選択対象をLLMが読み取り、質問をユーザーに投げる |
| ④ | 回答入力 | ユーザーは文章形式（図も利用可能）で回答する |
| ⑤ | 採点・FB | LLMは回答内容を採点しフィードバックを返す |
| ⑥ | 合否判定 | 基準点を下回っていればユーザーに再度回答させる |
| ⑦ | 繰り返し | ユーザーが中断するまで、またはすべての範囲をカバーするまで③〜⑥を繰り返す |

## 10. 欠けている観点・追加検討が必要な項目

> [!WARNING]
> 以下は検討シートで明示的に扱われていない、要件定義として補完が必要な観点です。

### 10.1 採点の詳細仕様

| 不足項目 | 説明 |
|:---|:---|
| **スコアのスケール** | 100点満点か、10点満点か、5段階か？スケールが未定義 |
| **採点基準の明文化** | LLMのFew-Shot例に載せる「良い回答」「悪い回答」の具体的な基準が未定義 |
| **部分点の扱い** | 論理的内容は正しいが物理的内容（引数等）が不正確な場合のスコア配分 |
| **再テスト時の質問変更** | 不合格時に同じ質問を出すのか、言い回しを変えるのか |

### 10.2 質問生成の制御

| 不足項目 | 説明 |
|:---|:---|
| **質問の粒度制御** | Chunk分割の具体的ルール（行数上限、ネスト深度、依存関係の扱い等） |
| **質問の順序** | ファイル内の定義順か、依存関係順（呼び出し元→呼び出し先）か |
| **対応言語** | Python以外（JS, TypeScript, Go等）のサポート範囲 |
| **質問の難易度調整** | 初回は簡単な質問から始める等の段階的アプローチ |

### 10.3 LLM応答のバリデーション

| 不足項目 | 説明 |
|:---|:---|
| **出力フォーマット** | LLMの応答をJSON等の構造化フォーマットで返させるかの仕様 |
| **ハルシネーション対策** | LLMが元コードにない内容で質問を作った場合の検出・排除 |
| **応答のリトライ** | LLMが不適切な出力をした場合のリトライ方針 |
| **レイテンシ目標** | ユーザー体験として許容できるLLM応答待ち時間 |

### 10.4 セッション管理の詳細

| 不足項目 | 説明 |
|:---|:---|
| **再開時の振る舞い** | 中断後に再開する際、前回の途中Chunkからか、不合格Chunkの再テストからか |
| **ファイル変更の検知** | 中断〜再開の間にソースコードが変更された場合の扱い（パス参照方式のリスク） |
| **セッション削除** | 古い履歴の削除やアーカイブの方針 |
| **進捗の可視化** | 全体の何%が完了しているかの表示仕様 |

### 10.5 エラーハンドリング

| 不足項目 | 説明 |
|:---|:---|
| **LLM接続エラー** | ローカルLLMが起動していない場合の通知・フォールバック |
| **ファイル読み込みエラー** | 存在しないパス、権限不足、バイナリファイル等の扱い |
| **大規模ファイル** | トークン上限を超える大きなファイルの分割戦略 |

### 10.6 ユーザー体験（UX）

| 不足項目 | 説明 |
|:---|:---|
| **回答のヒント機能** | ユーザーが全くわからない場合のヒント表示の有無 |
| **学習のゲーミフィケーション** | スコア推移のグラフ化、達成バッジ等のモチベーション設計 |
| **複数プロジェクトの管理** | 複数のWebアプリの理解負債を一覧・比較する機能 |
| **理解度ダッシュボード** | 全体の理解度をファイルごとに俯瞰する画面 |

### 10.7 セキュリティ・プライバシー

| 不足項目 | 説明 |
|:---|:---|
| **コードの外部送信** | API型LLMを使う場合、ソースコードが外部に送信されるリスクの許容範囲 |
| **機密コードの扱い** | 業務コードを扱う場合のデータ保護方針 |
